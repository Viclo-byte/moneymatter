## 3. 已确认：两个负债账户之间的本金结转

用户已明确确认：工商银行信用卡与独立分期账户均为负债账户。每期 **工商银行信用卡转出本金 → 独立分期负债账户转入本金**，信用卡另记利息支出；实际借记卡还款独立执行。这是业务方向的正式修订，无须再次确认方向。

### 3.1 余额表示与代码复核

负债账户以负余额表示欠款，余额更负表示欠款增加，趋近零表示欠款减少。手动信用卡和普通手动分期负债账户沿用项目已有的统一交易符号公式，不修改成另一套负债专用加减规则，也不能把“转出”理解成负债减少：

- 收入腿：`newBalance = oldBalance + amount`；在负债账户中表示欠款减少。
- 支出腿：`newBalance = oldBalance - amount`；在负债账户中表示欠款增加。
- `amount` 为正的 Money，方向由 `transactionType` 决定；不能传负数或对账户余额取绝对值后计算。
- 收入/支出是底层余额方向标记，是否计入收入/消费另由 `transferNature` 和统计策略判断。负债账户收到本金转入不构成收入统计。

### 3.2 完整余额示例：两边初始均有欠款

以下均为独立假设数据，非真实账本；本次本金 199.43、利息 29.67、合计 229.10，同币种 CNY。期初信用卡已有其他欠款 1,000.00，分期负债余额 -4,786.34，借记卡余额 10,000.00。原始消费和分期本金的初始归属已记妥。

| 步骤                      | 工商银行信用卡余额 | 独立分期负债余额 | 工商银行借记卡余额 | 三账户余额合计 | 本示例累计新增实际支出 |
| ------------------------- | -----------------: | ---------------: | -----------------: | -------------: | ---------------------: |
| 期初                      |          -1,000.00 |        -4,786.34 |          10,000.00 |       4,213.66 |                   0.00 |
| 本金内部转账完成          |          -1,199.43 |        -4,586.91 |          10,000.00 |       4,213.66 |                   0.00 |
| 信用卡另记利息支出        |          -1,229.10 |        -4,586.91 |          10,000.00 |       4,183.99 |                  29.67 |
| 之后借记卡实际还款 229.10 |          -1,000.00 |        -4,586.91 |           9,770.90 |       4,183.99 |                  29.67 |

逐笔交易结构如下，`T1`、`T2` 只是示意标识，实际由现有服务生成 UUID：

| 交易行              | 账户           | transactionType |   金额 | transferNature  | transferId | 收入/消费统计  |
| ------------------- | -------------- | --------------- | -----: | --------------- | ---------- | -------------- |
| P-out               | 工商银行信用卡 | expense         | 199.43 | common_transfer | T1         | 均不计入       |
| P-in                | 独立分期负债   | income          | 199.43 | common_transfer | T1         | 均不计入       |
| I                   | 工商银行信用卡 | expense         |  29.67 | not_transfer    | 无         | 利息支出 29.67 |
| R-out，后续独立操作 | 工商银行借记卡 | expense         | 229.10 | common_transfer | T2         | 均不计入       |
| R-in，后续独立操作  | 工商银行信用卡 | income          | 229.10 | common_transfer | T2         | 均不计入       |

计算：信用卡当期欠款增加 `199.43 + 29.67 = 229.10`；分期负债欠款减少 199.43；本金转账使两个负债合计不变，只有利息使合计欠款增加 29.67。实际还款只归还本期新增欠款，期初已有的 1,000.00 欠款仍在；不能误展示成全部信用卡欠款清零。新增收入统计始终为零，实际支出仅 29.67。

一期自动结算只生成 P-out、P-in、I 三行，不再创建一笔 229.10 的完整信用卡支出。后续真实还款另有 T2，不由分期自动任务生成，不共用 T1，也不纳入分期周期的撤销范围。上表是逐个业务环节展示；结算的本金两腿与利息对外必须原子提交，不能暴露部分成功。

撤销该期结算（在实际还款前单独验证）：信用卡撤销本金影响 +199.43、撤销利息影响 +29.67，回到 -1,000.00；分期负债撤销转入影响 -199.43，回到 -4,786.34；借记卡仍 10,000.00，新增支出回到零。若实际还款已存在，它是独立真实交易，撤销分期结算不能擅自删除它；此时保留实际还款后的余额影响，并向用户展示预计变化。

首次将原信用卡账单本金归入独立分期负债，应已完成一次真实的初始重分类；如没有，必须先展示期初结构，不能再次计入全部原始消费或重复建债。

### 3.3 金额验证结果与限度

2026-11-18 本地验证通过 **18 个精确金额断言**：直接导入项目 Money，提取并执行现有 `calculateNewBalance` 和 `defineCorrectAmountFromTxType` 纯函数，覆盖双负余额、本金转账合计守恒、利息、独立还款、撤销、首期差异、累计本金尾差与零本金/零利息。反例也已验证：错误地让 -4,786.34 的分期账户转出 199.43，会变成 -4,985.77，使欠款增加。

这验证了现有余额公式和示例计算；transferId 生成、事务及统计过滤已做源码复核，但尚未执行数据库集成测试，不能把公式验证当作三行真实交易、并发、统计报表和回滚已经通过。

### 3.4 账户兼容边界与统计例外

- 普通 `system` 手动负债账户：使用 `common_transfer`，支持上述方向与余额机制。初版只接受本人同币种、不同账户，并排除专用贷款/车辆类别。
- `loan` + `LoanDetails`：存在专门的 `transfer_to_loan`、超还保护及锚点重算。现有统计会把该转账的 expense 腿计入支出；仅方向正确仍不足以满足“本金不入消费”。**修正上一版报告对转账排除统计的概括：初版明确拒绝这类关联**，不能用 common_transfer 绕过贷款模型。未来若支持，需同时设计结算来源标识和限定于分期本金的统计排除，验证全部相关报表，并保持原普通贷款还款统计语义。
- 历史 `loan` 分类但无 `LoanDetails`：常规余额更新对 loan 类别直接返回，不能当作普通账户；初版拒绝并提供兼容说明，不自动改类别或余额。
- 银行同步账户：现有服务禁止手动新增真实交易，不能伪造 accountType 绕过；跨用户共享、车辆及跨币种关联也不纳入首版。普通定期收支原有行为保持现状。
- 利息使用 `not_transfer`、明确利息分类，不能被本金的统计排除设置一并屏蔽。实现时核对信用卡账户及利息交易的 `excludeFromStats`；如账户整体排除，预览须提示无法满足利息计入统计的要求，禁止静默覆盖用户全局设置。

## 4. 建议数据库方案（尚未实施）

优先采用现有订阅的可选侧表，避免另一套定期任务系统。

### InstallmentPlans

每个 subscription 至多一行：`subscriptionId` 唯一外键、币种、`totalPrincipal`、`amountMode`（fixed/custom）、首期/常规/末期本金和利息模板、`linkedSettlementEnabled`、`sourceAccountId`（已确认：工商银行信用卡）、`destinationAccountId`（已确认：独立分期负债）、`interestCategoryId`、`revision`。首期日期映射原有首次 dueDate；单期特殊日期在明细保存。仅 `type=installment` 可创建侧表。

### InstallmentScheduleItems

保存全部期数：`id`、`planId`、`occurrenceNumber`、`dueDate`、`principal`、`interest`、`total`、`isManualOverride`、`revision`、`periodId`（可空，唯一）、取消/提前结清标记。`UNIQUE(planId, occurrenceNumber)`，金额字段复用 MoneyField 的整数分，CHECK：本息非负、`total=principal+interest`、期号大于零。只有当前可执行期绑定 SubscriptionPeriods；未来金额行不是开放付款周期。

### InstallmentSettlements / InstallmentSettlementTransactions

结算头保存 `scheduleItemId`、`periodId`、`generation`、`state`（settled/reverted）、请求幂等键、实际日期、本息币种及账户快照、结清标志。仅一个有效结算对应某个周期/计划明细（部分唯一索引），`UNIQUE(periodId,generation)`，幂等键唯一。撤销后可以用新幂等键再次付款，但旧请求重试不能重放。

交易关联表记录结算、交易 ID、role（principal-out / principal-in / interest）、`transferId`、是否系统生成；每个结算每个角色唯一，交易唯一归属。零本金或零利息不创建零额交易。保存实际结算快照，后续修改模板不能影响已结算历史。

引用受控交易不能使用静默 SET NULL 掩盖财务关联丢失。拟用受控删除顺序与限制性外键；撤销前保存审计快照，再解除/归档活跃关联，最后调用原有删除服务。已撤销结算不得依赖被永久删除的交易行。数据库约束与迁移实现时需覆盖这个顺序。

### 迁移与历史

新增 migration，不改既有已发布迁移。老订阅没有侧表，全部按旧逻辑。既有分期只有用户显式启用新计划时才转换，显示历史已付本金录入与剩余本金对账，不能从旧的总支出金额猜本息。迁移需在独立测试数据库验证 up/down；已有新财务记录后回退应用版本须先停用新模式并按数据兼容流程处理，不能直接删除表。

## 5. 金额计划与日期规则

1. 首期、常规、末期独立输入，本金 + 利息必须等于总额。用户手工输入三项不一致时拒绝保存，不偷偷改首期。
2. fixed 只展开常规期；custom 每期独立。单期分期同时是首末期，以唯一明细为准，避免模板互相覆盖。
3. 末期本金 = 总本金 - 已结算本金 - 其他保留计划本金。结果为负则拒绝并展示超额；零本金可保留正利息，不能用截断为零掩盖超还。
4. 例如总本金 4,786.34、24 期、首期本金 199.45、第 2–23 期各 199.43，则末期本金 199.43；若总本金为 4,786.35，末期为 199.44。
5. 修改未付款项时锁计划并验证 revision，只调整系统生成的未来未付项/末期尾差，保留手动覆盖；预览差额后保存。已结算本金与利息保持快照；已付款项不可直接修改。
6. 日期使用已有 recurrence、anchorDay 和 DATEONLY 约定；首期可不同，中间期可覆盖，须保持执行顺序明确。所有未来日期展示采用现有项目时区规则，初版不擅自改造 UTC 日期语义。
7. 计划累计本金必须精确等于 totalPrincipal；同时不得超过关联账户可偿还本金（已锁账户状态）。关联账户如有非本计划交易造成差异，停止自动付款并要求对账。
8. 跳过并不等于偿还本金。新模式不能直接沿用“skipped 计入完成且本金消失”；建议初版关闭跳过，允许延期/编辑未付日期。普通分期原有跳过语义不变。

## 6. 结算、并发、撤销与提前结清

扩展现有 `markPeriodPaid`：无新计划走原分支；启用逐期计划但不关联负债时，按当期 total 生成旧式普通付款（保留既有支出统计语义）；关联负债时进入本息结算分支。只有后者的本金从消费中排除。

结算流程：验证归属与模式 → 开事务 → 按统一顺序锁订阅/计划、周期、明细，再按账户 ID 顺序锁账户 → 重新校验状态和 revision → 查幂等键/有效结算 → 读取本息 → 创建本金真实双边转账 → 创建正额利息支出 → 保存结算快照和各腿关联 → 标记周期已付、推进一个执行周期并绑定下一金额项 → 按本金实际结清状态决定完成 → 提交。

转账创建使用现有 `createTransaction` 及 `destinationAccountId` / `destinationAmount` 参数，使用正数 Money；保持 `withoutPeriodSettlement` 上下文避免新交易被现有自动匹配重复认领。任一步失败回滚所有交易、余额、结算、付款状态和后继周期。死锁只在外层有限重试，不在已经失败的事务内继续。

### 6.1 自动化分支的确定设计

沿用 `process-auto-record → markPeriodPaid`，不创建第二个分期调度器，也不让通用付款先生成 total 支出后再执行本息分解。在任何交易写入前按计划配置选择互斥分支：

1. 没有新计划：执行现有普通定期付款逻辑。
2. 有逐期计划但未启用关联负债：读取当期 total，执行原单笔付款逻辑。
3. 启用关联负债：直接执行以下结算，完全跳过原有完整金额付款 builder。

新分支的源参数固定为信用卡账户 ID（同时作为利息账户），目标为独立分期负债账户 ID。本金使用 `Money.fromDecimal` 或既有 MoneyField 读取值：`accountId=信用卡`、`transactionType=expense`、`amount=本期principal`、`destinationAccountId=分期负债`、`destinationAmount=同一本金`、`transferNature=common_transfer`，`isPlanned=false`；不传 accountType 绕过类型解析，不传 destinationTransactionId 关联任意旧行。调用现有 `createTransaction` 一次，读取其返回的两腿，验证同一非空 transferId、相反方向、正确账户和相同金额后保存关联。

利息另外调用 `createTransaction`，参数为 `accountId=信用卡`、`transactionType=expense`、`amount=本期interest`、`transferNature=not_transfer`、`categoryId=利息分类`、`categoryIdIsExplicit=true`。保存后核对最终分类及统计标记，防止收款人分类规则覆盖为其他分类。两次创建都包在 `withoutPeriodSettlement` 中、加入同一外层事务，并共用本期实际记账日期；若任意验证不通过，整体回滚。

写入周期已付之前，用 Money 核对：计划 total = principal + interest，实际信用卡本金转出金额 + 实际利息金额 = total，分期转入金额 = principal；不得用正负腿互抵后的零来冒充银行扣款总额。保存双方账户 ID、币种、本息、transferId 和交易 ID 快照，周期关联以结算头为准，不能只拿利息 transactionId 代表整期。

零本金只创建正额利息；零利息只创建本金两腿；本息全零初版拒绝自动记账并提示检查计划。调度只执行当前已绑定周期，不扫描全部未来金额明细创建交易；后继周期只绑定下一未结算计划。现有对 overdue 的处理保持现状。

自动任务、手动付款及 MCP 共用同一有效结算唯一约束和事务入口；幂等键由“周期 + 当前结算 generation”稳定派生并记录，界面双击或定时任务重试不能生成新 generation。只有受控撤销成功才开启下一 generation，旧 generation 请求不得重放。实际还款不在这条入口执行，需用户另行记账或已有独立还款流程触发。

### 6.2 并发、撤销与提前结清

并发自动任务、手动点击、MCP、编辑和撤销共享锁顺序。相同幂等键返回原结果；不同请求争用同一期返回已结算冲突，不再创建第二组交易。不能只靠 cron 的单实例或先查询状态保证幂等。

撤销锁同一结算单元，核对三腿、权限、账户状态及是否被改动；调用既有转账删除服务一次撤销本金两腿，另撤销利息，恢复周期及计划执行状态，结算归档为 reverted，清除完成状态。任何一腿不能撤销则整体拒绝，不能只重开周期。普通 LINK 模式继续不删除用户交易。新关联模式初版只支持系统创建，不允许单笔 LINK 或“仅标已付”跳过财务结算。

受控交易从普通交易编辑/删除/Trash 恢复进入时，应明确引导到整个分期结算操作；不得允许单腿修改、删除后重新付款，再恢复旧腿重复记账。后续如支持导入交易匹配，必须验证整组双边转账和利息，不仅关联其中一笔。

提前结清复用同一结算路径，记录实际清偿本金、费用或利息；校验不超过剩余本金，仅全部清偿时关闭后续期数；部分清偿重算未付计划。后续明细保留为取消，不删除已付历史。结清后撤销恢复此前未付款项和计划 revision 快照，不能丢失自定义安排或重建已付记录。借记卡实际还款仍由独立普通转账完成。

## 9. 确认状态与后续实施边界

已确认：用户于 2026-11-18 确认以信用卡转出本金、分期负债转入本金；两者均为负债账户。现有普通手动负债账户的余额公式、两腿构造与 common_transfer 默认统计过滤已复核，自动化设计已按此展开。此次继续设计不视为批准修改业务代码或发布。

其余设计建议保留供实现前审阅：

1. 本金方向已确定，后续不得再使用需求快照中的旧方向。
2. 首版支持本人同币种手动普通账户；受管理贷款因专用余额与统计规则，在专门兼容方案通过前拒绝关联。
3. 新计划模式禁用跳过；关联结算只允许整组创建与撤销，实际信用卡还款独立。
4. 采用独立逐期金额侧表与现有滚动周期组合；旧分期显式转换，历史本息由用户对账确认。

确认不等于自动发布。实施顺序：金额计划与迁移 → 原有入口本息结算 → 撤销/结清/保护 → API/MCP/前端/i18n → 完整验收 → PR 审核 → 单独发布。
