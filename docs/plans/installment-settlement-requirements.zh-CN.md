项目地址：

https://github.com/Viclo-byte/moneymatter

# 三、第二阶段：增强分期付款金额管理

这是本次重点功能之一。

目前很多银行的分期付款并不是每一期金额完全相同。

例如：

- 首期因为办理日期或计息周期不同，金额与后续期数不同。
- 首期可能有不同的本金和利息。
- 中间每期金额相同。
- 最后一期可能存在尾差调整。
- 某些银行每一期本金和利息都不相同。

因此，希望在现有定期收支的分期付款设置中增加更灵活的金额管理机制。

## 3.1 新增首期金额设置

在现有分期付款设置中增加：

「首期付款设置」

支持分别设置：

- 首期实际付款总额。
- 首期偿还本金。
- 首期利息。
- 首期付款日期。

例如：

首期：

- 总额：227.18
- 本金：199.45
- 利息：27.73

后续常规期数：

- 每期总额：229.10
- 本金：199.43
- 利息：29.67

首期金额不能被系统强制设置为与后续期数相同。

## 3.2 常规期数设置

支持设置：

- 后续每期预计付款金额。
- 每期本金。
- 每期利息。
- 付款频率。
- 每期付款日期。

允许用户选择：

A. 固定金额模式

后续每期本金、利息和总额保持一致。

B. 自定义金额模式

允许每一期设置不同的本金和利息。

## 3.3 最后一期设置

增加：

「最后一期付款设置」

支持：

- 自动计算剩余本金。
- 自动调整最后一期本金。
- 自定义最后一期利息。
- 自定义最后一期实际付款金额。
- 允许最后一期与常规期数金额不同。

最后一期不能因为四舍五入而产生负数余额或多还本金。

## 3.4 每期明细管理

建议在定期分期付款详情中增加一个「分期付款计划」列表。

例如：

| 期数   |     本金 |   利息 |   总金额 | 状态   |
| ------ | -------: | -----: | -------: | ------ |
| 第1期  |   199.45 |  27.73 |   227.18 | 已付款 |
| 第2期  |   199.43 |  29.67 |   229.10 | 待付款 |
| 第3期  |   199.43 |  29.67 |   229.10 | 待付款 |
| 第4期  |   199.43 |  29.67 |   229.10 | 待付款 |
| ...    |      ... |    ... |      ... | ...    |
| 第24期 | 自动计算 | 自定义 | 自动计算 | 待付款 |

具体要求：

- 可以查看全部期数。
- 可以单独编辑尚未付款的期数。
- 已付款期数不能被意外覆盖。
- 支持调整首期、任意中间期和末期金额。
- 每一期的本金、利息和总金额必须保持一致。
- 修改某一期金额时，重新计算剩余未付款计划，但不得擅自修改已结算历史记录。
- 所有金额使用 Decimal 或项目现有的精确货币计算机制，避免浮点误差。

建议采用每期独立的付款计划数据，而不是仅依赖一个固定的 recurring amount。

# 四、第三阶段：关联分期负债账户与自动内部转账

这是本次另一个核心功能。

## 4.1 业务背景

用户可能会建立一个独立的负债账户，用来追踪信用卡账单分期的剩余本金。

例如：

账户A：工商银行信用卡。

账户B：工商银行10月账单分期本金。

每期分期付款包含本金和利息。

需要在每月到期时：

1. 分期负债账户向信用卡账户进行本金内部转账。
2. 信用卡账户单独记录本期利息支出。
3. 两者合计等于本期银行分期扣款金额。

## 4.2 新增关联账户设置

在现有分期付款编辑页面增加一个可选区域：

「关联分期负债账户」

支持：

- 开启或关闭关联负债账户。
- 选择独立分期负债账户。
- 设置转出账户。
- 设置转入账户。
- 自动使用每期计划中的本金金额。
- 跟随现有定期付款日期执行。
- 跟随现有分期期数执行。

不要另外开发一套独立的定期转账管理系统，优先扩展现有定期收支的执行机制。

## 4.3 必须使用内部转账逻辑

**非常重要：本金减少必须通过 MoneyMatter 现有的真实双边内部转账机制完成。**

禁止：

- 直接修改负债账户余额。
- 直接增加或减少账户余额作为替代。
- 创建没有对应账户的单边负债减少记录。
- 将本金偿还计入收入或普通消费。
- 使用两笔互不关联的收入和支出模拟转账。

正确流程：

交易A：分期本金内部转账。

- 转出：独立分期负债账户。
- 转入：工商银行信用卡。
- 金额：本期实际偿还本金。
- 两笔交易使用同一个 transferId。
- 不计入收入和消费统计。

交易B：信用卡利息支出。

- 账户：工商银行信用卡。
- 金额：本期实际利息。
- 分类：利息支出。
- 计入实际支出统计。

两笔交易合计必须等于本期银行分期扣款金额。

例如：

本金：199.43

利息：29.67

本期总额：229.10

内部转账199.43 + 利息支出29.67 = 信用卡本期分期金额229.10。

注意：这里的内部转账必须经过现有账户余额计算机制，特别检查负数负债账户作为转出账户时的余额变化是否正确。

如果现有内部转账机制不支持负债账户，请先提出兼容方案，不要绕过原有账本机制。

# 五、第四阶段：自动记录付款与关联转账整合

本次功能应当直接建立在现有定期收支的自动记录付款机制上。

用户开启自动记录付款后，系统每期自动执行：

1. 读取当前期的付款计划。
2. 获取本期本金及利息金额。
3. 生成本金内部转账。
4. 生成信用卡利息支出。
5. 检查两者总额是否等于本期实际付款金额。
6. 将本期标记为已付款。
7. 更新下一期付款计划。

如果用户没有开启关联负债账户，则继续使用原有定期付款行为，不影响普通订阅和定期收支。

如果用户开启关联负债账户，则执行分期结算流程。

**不要同时生成一笔完整金额的信用卡支出，再额外生成本金转账和利息支出。**

否则会导致重复记账。

正确的信用卡账户变化应该是：

- 收到本金内部转账。
- 记录利息支出。

两者合计就是银行实际分期扣款金额。

# 六、第五阶段：实际还款流程

用户实际偿还信用卡时，仍然使用普通借记卡向信用卡转账。

例如：

工商银行借记卡转账229.10元至工商银行信用卡。

这是独立于分期结算的另一笔真实资金转移。

不得将实际信用卡还款与分期本金内部转账混为一谈。

整个业务流程：

1. 分期账户向信用卡结转本金。
2. 信用卡记录当期利息。
3. 借记卡实际向信用卡还款。

三个环节必须保持独立，不能重复生成交易。

# 七、第六阶段：自动化安全与数据一致性

财务系统必须保证数据准确性。

请重点实现：

## 幂等性

同一个付款周期不能重复生成内部转账或利息交易。

## 原子性

本金双边转账、利息支出和付款周期状态更新应当作为一个完整结算单元。

任何一步失败，必须整体回滚。

## 撤销机制

撤销已付款周期时：

- 撤销对应本金内部转账。
- 撤销对应利息支出。
- 恢复分期账户及信用卡账户的余额。
- 将付款周期恢复为未付款状态。

## 修改机制

用户修改未付款期数的本金或利息时：

- 只影响对应未结算计划。
- 正确更新未来付款计划。
- 不修改已完成的历史交易。

## 提前结清

支持用户提前结清分期：

- 允许录入提前结清本金。
- 允许录入提前结清手续费或剩余利息。
- 通过内部转账处理实际结清本金。
- 记录真实费用。
- 结束后续付款周期。
